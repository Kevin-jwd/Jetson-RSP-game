# 모듈 구조와 동작

웹캠 프레임 하나가 승패 판정이 되기까지 거치는 경로는 이렇습니다.

```
카메라 ──> app.py ──> detector.py ──> cuda.py ──> TensorRT 엔진
                          │
                          v
                    [Detection, ...]
                          │
              app.py ──> logic.py ──> Round(승/패)
                          │
                          v
                 화면 + particles.py
```

핵심 경계는 **`detect(frame) -> list[Detection]`** 하나입니다. 게임 로직과 화면은
추론이 무엇으로 도는지 모릅니다. 그래서 백엔드를 onnxruntime에서 TensorRT로 바꾸는
동안에도 `logic.py`와 화면 코드는 손대지 않았습니다.

| 파일 | 줄 수 | 역할 |
| --- | --- | --- |
| `main.py` | 25 | 명령줄 인자 파싱, `Game` 실행 |
| `rps/detector.py` | 197 | 엔진 로딩, 전처리, 추론, 디코딩, NMS |
| `rps/cuda.py` | 80 | GPU 메모리 할당과 복사 |
| `rps/logic.py` | 28 | 승패 규칙과 결과 값 |
| `rps/app.py` | 435 | 라운드 상태 머신, 입력, 렌더링 |
| `rps/particles.py` | 97 | 승자 파티클 효과 |
| `rps/retro.py` | 79 | 픽셀 글씨, 스캔라인, 깜빡이는 문구 |
| `tools/probe.py` | 80 | 엔진이 실제로 무엇을 내놓는지 확인 |
| `tools/cuda_check.py` | 59 | CUDA/TensorRT 실행 환경 점검 |
| `tools/merge_dataset.py` | 125 | 데이터셋 병합과 클래스 재매핑 |

## main.py

`argparse`로 인자를 받아 `Game`을 만들고 `run()`을 부르는 것이 전부입니다.

| 인자 | 기본값 | 의미 |
| --- | --- | --- |
| `--model` | `models/rps_yolo11n_2.engine` | TensorRT 엔진 경로 |
| `--camera` | `0` | `/dev/video*` 번호 |
| `--conf` | `0.5` | 신뢰도 임계값 |
| `--classes` | 없음 | 엔진의 클래스 순서를 직접 지정 |
| `--no-mirror` | 꺼짐 | 좌우 반전 끄기 |

`--classes`는 쉼표로 구분한 문자열을 리스트로 잘라 넘깁니다. 옛 모델처럼 클래스
순서가 다른 엔진을 쓸 때 코드를 고치지 않고 맞추기 위한 탈출구입니다.

## rps/detector.py

엔진을 직접 다루는 유일한 곳입니다. torch도 ultralytics도 쓰지 않고, JetPack이
제공하는 `tensorrt` 모듈만 사용합니다.

### 로딩 순서가 중요한 이유

`Detector.__init__`은 이 순서를 지킵니다.

1. **`CudaMemory()` 먼저** — pycuda가 자기 CUDA 컨텍스트를 만들어 현재 컨텍스트로
   설정합니다.
2. 그 다음에 엔진 역직렬화와 실행 컨텍스트 생성

순서가 뒤바뀌면 엔진은 A 컨텍스트에서 만들어지고 실행은 B 컨텍스트에서 일어나,
커널 실행 단계에서 `Cask (Cask convolution execution)` 오류로 죽습니다. 실제로
겪은 문제라 주석으로 남겨두었습니다.

### 엔진에서 읽어오는 것들

하드코딩하지 않고 엔진에 물어봅니다.

- **입출력 텐서 이름** — `get_tensor_mode`로 INPUT/OUTPUT을 구분
- **shape** — 동적 엔진이면 `-1`이 오므로, 최적화 프로파일의 opt 값으로 고정한 뒤
  `set_input_shape`을 호출합니다. 이걸 안 하면 `-1`이 그대로 곱해져 버퍼 크기가
  망가집니다.
- **dtype** — FP16 엔진에 float32 버퍼를 넣는 것도 같은 `Cask` 오류의 원인입니다.
- **입력 해상도** — `self.size = in_shape[2]`. 그래서 320 모델이든 640 모델이든
  코드 변경 없이 동작합니다.

### 클래스 이름의 우선순위

```
--classes  >  엔진의 JSON 헤더  >  CLASS_NAMES 폴백
```

ultralytics가 export한 엔진은 파일 앞에 4바이트 길이 + JSON 헤더가 붙어 있어
`_split_engine()`이 그걸 분리해 `names`를 읽습니다. `trtexec`으로 만든 엔진에는
헤더가 없어 파일 전체가 엔진이고, `CLASS_NAMES`가 쓰입니다.

`CLASS_NAMES = {0: "paper", 1: "rock", 2: "scissors"}` — Roboflow 데이터셋 순서입니다.
**이 순서가 어긋나면 rock만 맞고 paper와 scissors가 뒤바뀝니다.** rock이 두 순서
모두에서 1번이기 때문인데, 이 증상이 보이면 정확도가 아니라 순서를 의심하세요.

### detect()의 흐름

1. **letterbox** — 종횡비를 유지한 채 정사각형으로 리사이즈하고 남는 곳을 114로
   채웁니다. 되돌릴 때 필요한 배율 `r`과 여백 `left/top`을 함께 반환합니다.
2. **blob 생성** — BGR을 RGB로 뒤집고 `(1, 3, size, size)`로 축을 바꾼 뒤 255로 나눕니다.
   엔진의 dtype으로 변환하고 `ascontiguousarray`로 메모리를 정렬합니다.
3. **추론** — `_infer()`가 GPU로 복사, 실행, 회수를 담당합니다.
4. **디코딩** — 출력 `(1, 4+nc, anchors)`를 전치해 앵커별로 봅니다. 4개는 `cx, cy, w, h`,
   나머지는 클래스별 점수입니다. 최대 점수가 임계값을 넘는 것만 남깁니다.
5. **좌표 복원** — 중심-크기를 모서리 좌표로 바꾸고, letterbox 여백을 빼고 배율로
   나눠 원본 프레임 좌표로 되돌린 뒤 프레임 경계로 clip합니다.
6. **NMS** — 클래스를 구분하지 않는 NMS입니다. 손 하나가 라벨 두 개를 만드는 것을
   막기 위해서입니다.

### _infer()의 방어

`execute_async_v3`가 실패하면 구형 `execute_v2`로 한 번 폴백하고, 그것도 실패하면
예외를 던집니다. 실패를 무시하면 직전 출력 버퍼가 그대로 남아 **"모델이 조용히
아무것도 못 찾은 것"처럼 보입니다.** 실제로 이것 때문에 원인 파악이 늦어졌습니다.

알 수 없는 클래스 id도 버리지 않고 숫자를 라벨로 씁니다. 같은 이유입니다 — 조용히
버리면 검출 실패와 구분이 안 됩니다.

## rps/cuda.py

TensorRT에 넘길 GPU 버퍼를 다룹니다. JetPack 버전에 따라 `cuda-python` 또는
`pycuda` 중 설치된 쪽을 자동으로 고릅니다.

제공하는 것은 네 가지뿐입니다: `alloc(nbytes)`, `htod(dst, src)`, `dtoh(dst, src)`,
`sync()`. 그리고 `stream = 0`.

**기본 스트림에 동기 복사**를 씁니다. 프레임 하나씩 처리하는 게임에는 별도 스트림이
필요 없고, TensorRT가 실행하지 못하는 스트림 핸들은 디버깅이 몹시 어렵기 때문에
변수 자체를 없앴습니다.

## rps/logic.py

순수 함수만 있는 곳입니다. 카메라도 pygame도 모릅니다.

```python
BEATS = {"rock": "scissors", "scissors": "paper", "paper": "rock"}
```

- **`judge(a, b)`** — 두 수를 받아 각자 관점의 `WIN`/`LOSE`/`DRAW`를 돌려줍니다.
- **`Round`** — 좌/우 손과 각자의 결과를 담는 값입니다.

좌/우는 라벨이 아니라 **좌표로** 결정됩니다. 정렬은 `app.py`의 `_collect`가 합니다. 그래서 데이터셋에 "왼손 가위" 같은
클래스가 필요 없고, 클래스는 3개로 충분합니다.

`BEATS`에 없는 라벨은 `app.py`의 `_collect`가 걸러냅니다. 엔진이 예상 밖의 클래스 id를
내도 `KeyError`로 죽지 않습니다.

## rps/app.py

가장 큰 모듈이고, 상태 머신과 렌더링이 같이 있습니다.

### 상태 흐름

```
MENU ──1인용 / 2인용──> COUNTDOWN ──3초──> SHOOT ──0.7초 투표──> RESULT
 ^                                                                  │
 └──── OVER (크레딧 0) ─────────────────────────────────────────────┘
 ^                                                                          │
 └──────────────────── 종료 버튼 ────────────────────────── 재시도 ─────────┘
```

- **MENU** — 타이틀과 모드 버튼 두 개. 추론을 돌리지 않습니다.
- **COUNTDOWN** — `가위`/`바위`/`보!`를 각 1초씩 영상 위 중앙에 띄웁니다. 패널이
  아니라 영상 위인 이유는 플레이어가 카메라를 보고 있어야 하기 때문입니다.
- **SHOOT** — 0.7초 동안 매 프레임 추론하며 손마다 라벨을 투표로 모읍니다. 손이 아예
  안 보이면 1.5초에 포기하고 "손이 안 보여요"로 넘어갑니다. 멈추지 않습니다.
- **RESULT** — 판정 순간의 프레임을 **정지 화면으로 고정**합니다. 무엇을 보고
  판정했는지 확인할 수 있어야 하기 때문입니다. 이후는 모드에 따라 갈립니다.
  - **vs Person** — 버튼을 기다립니다. 두 사람이 손을 바꿔 가며 다시 준비할 시간이
    필요하고, 준비되는 타이밍은 사람마다 다르기 때문입니다. `재시도` / `종료`
  - **vs AI** — 3초 뒤 다음 라운드가 자동으로 시작됩니다. 혼자 하는 만큼 매번
    버튼을 누르는 게 번거롭기 때문입니다. 그래서 이 모드에서는 `재시도` 대신
    `종료`만 보여줍니다.

### 크레딧

1인용은 아케이드 기판처럼 크레딧으로 돕니다. 크레딧이 있어야 시작할 수 있고,
**지는 라운드만 1을 소모합니다.** 이기거나 비기면 그대로 유지되므로 잘하는 사람은
계속 할 수 있습니다 — 오락실 기계가 실력에 보상을 주던 방식입니다. 손을 못 읽어
판정이 없었던 라운드도 차감하지 않습니다.

`c` 키로 코인을 넣고(최대 9), 0이 되면 `OVER` 상태로 3.5초간 GAME OVER를 띄운 뒤
타이틀로 돌아갑니다. 2인용은 크레딧을 쓰지 않습니다.

시간은 `pygame.time.get_ticks()`와 `self.since` 차이로만 잽니다. 상태 진입 시각
하나만 기억하면 되어서 타이머 객체가 필요 없습니다.

### 왜 한 프레임으로 판정하지 않는가

처음에는 두 손이 잡히는 **첫 프레임**으로 바로 판정했습니다. 그런데 `SHOOT`는 "보!"
박자가 끝나는 순간 시작되고, 그때 손은 아직 움직이는 중입니다. 주먹이 보로 펴지는
중간 형태가 `scissors`로, 그것도 높은 신뢰도로 읽히는 일이 실제로 있었습니다.
가장 불리한 프레임을 골라 판정하고 있었던 셈입니다.

제스처가 눈에 보이는 형태로 안정되는 데 수백 ms가 걸린다는 건 측정된 사실이기도
합니다([EMG 연구](https://arxiv.org/abs/2606.29423)에서 근육 활동이 시각적 onset보다
342ms 앞섭니다).

그래서 `VOTE_MS = 700` 동안 투표를 모읍니다.

- **`_collect`** — 매 프레임 손을 x좌표로 정렬해 슬롯에 넣고, 슬롯별로
  `{라벨: (프레임 수, 신뢰도 합)}`을 누적합니다. 좌표로 정렬하므로 박스가 움직여도
  슬롯 0은 계속 같은 사람입니다.
- **`_decide`** — 슬롯마다 최다 득표 라벨을 고릅니다. 동점이면 신뢰도 합이 높은 쪽입니다.
  결과 화면의 박스 라벨도 이 값으로 바꿔 표시합니다. 화면과 판정이 어긋나면
  혼란스럽기 때문입니다.

0.7초는 [Nielsen의 반응 시간 한계](https://www.nngroup.com/articles/response-times-3-important-limits/)에서
"사고 흐름이 끊기지 않는" 1초 안쪽이고, 원래 가위바위보도 낸 손을 잠깐 확인하는
게임이라 어색하지 않습니다.

vs AI 모드는 신뢰도가 가장 높은 손 **하나만** 투표 대상으로 삼습니다. AI의 수는
라운드 시작 시점에 `random.choice`로 뽑아둔 값을 씁니다.

**AI의 수는 검출기를 거치지 않습니다.** 이미 알고 있는 값을 이미지로 그려서 다시
검출하는 것은 추론을 한 번 더 쓰면서 정답을 잃을 위험만 더합니다. 이미지는 순수하게
표시용이고, 왼쪽 절반에 고정으로 그려집니다.

라운드 시작 때 미리 뽑아두는 이유는, 사람 손을 못 읽었을 때도 AI가 낸 수는 보여주기
위해서입니다.

### 이미지와 폰트의 폴백

- **AI 손 이미지** — `assets/rock.png` 등을 찾아 영상 높이의 55%로 비율을 유지해
  축소합니다. 없으면 이름이 적힌 카드를 그리고 시작할 때 어떤 파일이 없는지 알립니다.
- **한글 폰트** — `pygame.font.match_font`로 확인하고, 없으면 `GAWI/BAWI/BO!`,
  `START/RETRY/QUIT`으로 자동 대체합니다. 없는 폰트로 렌더링하면 글자가 네모로
  깨지기 때문입니다.

### 렌더링에서 정한 것들

- 검출된 박스는 **전부** 그립니다. 판정에 쓰인 것만 그리면 "손이 없는 것"과
  "한 손만 있는 것"을 구분할 수 없습니다. 판정에 쓰인 박스는 승패 색, 나머지는 회색입니다.
- 파티클은 영상 영역으로 클리핑해 패널을 침범하지 않게 합니다.
- 하단 힌트에 FPS와 검출 개수를 항상 표시합니다. 문제가 생겼을 때 화면만 보고
  원인을 좁힐 수 있어야 하기 때문입니다.

## rps/particles.py

승자 손 위에서 터지는 파티클입니다. 참고한 프로젝트에 라이선스가 없어 코드는
가져오지 않고 방식만 따랐습니다.

각 파티클은 무작위 방향으로 90~340 px/s로 출발해 중력(420 px/s²)과 공기저항을
받으며 0.6~1.2초 동안 사라집니다. 색은 7가지 무지개 팔레트에서 무작위로 고릅니다.

**원 이미지는 색·반지름 조합별로 캐싱**하고 `set_alpha`만 바꿔 재사용합니다. 매
프레임 파티클마다 Surface를 새로 만들면 Jetson에서 프레임이 떨어집니다.

무승부에는 파티클이 없습니다. 축하할 승자가 없기 때문입니다.

## tools/

게임과 분리된 진단·데이터 도구입니다.

### probe.py

GUI 없이 엔진의 입출력 shape과 dtype, 클래스 이름을 출력하고, 임계값을 매우 낮춰
프레임별 검출 결과와 **임계값과 무관한 최고 점수**를 찍습니다.

화면에 아무것도 안 나올 때 원인을 셋으로 가릅니다.

| 출력 | 의미 |
| --- | --- |
| `best_score`가 높은데 `kept=0` | 임계값이 높음 → `--conf`를 낮추면 됨 |
| `best_score`도 낮음 | 모델이 정말 못 찾는 것 |
| 라벨이 숫자로 표시됨 | 클래스 순서 불일치 |

### cuda_check.py

TensorRT 버전, CUDA 런타임/드라이버 버전, GPU 이름, 여유 메모리를 출력하고 디바이스
메모리 왕복 복사를 시험합니다. 커널 단계에서 실패할 때 "환경 문제인지 코드 문제인지"를
가르는 용도입니다.

### merge_dataset.py

여러 YOLO 데이터셋을 하나로 합치면서 **클래스 이름 기준으로 id를 재매핑**합니다.
공개 데이터셋은 보통 알파벳순(`Paper, Rock, Scissors`)이고 이 게임은
`scissors, rock, paper` 순서를 쓰던 시기가 있어, 그냥 합치면 조용히 뒤바뀝니다.

`images/train` 구조와 `train/images` 구조를 모두 인식하고, 파일명 충돌을 막기 위해
원본 폴더 이름을 접두사로 붙입니다. `valid`는 `val`로 통일합니다.
